## 项目文档

本项目由五份文档维护。开始任何工作前先读 `STATUS.md` 和 `docs/plan.md`。

| 文件 | 内容 | 谁在什么时候改 |
| --- | --- | --- |
| `docs/plan.md` | 科学问题、核心假设、判定标准。不含实现细节。 | 只在科学判断本身改变时改，需先说明理由。 |
| `docs/roadmap.md` | 任务节点、状态、每个节点服务于哪条假设。不含动机论述。 | 节点状态变化时改。 |
| `docs/decisions.md` | 已做出的技术选择、当时的理由、失效条件。只追加，不修改历史条目。 | 每次做出影响后续工作的选择时追加一条。 |
| `docs/ISSUES.md` | 尚未解决但未造成硬阻塞的问题、证据缺口和升级条件。不是任务清单。 | 问题发现、状态变化、解决或升级为硬阻塞时更新。 |
| `STATUS.md` | 项目当前状态的通俗概述。 | 每个工作日结束时重写。 |

### 工作时的约束

- 完成一个 roadmap 节点后，明确回答：这个结果对 `docs/plan.md` 里的哪条假设产生了什么影响。如果答案是"没有影响"，在 `docs/roadmap.md` 中把该节点标记为基础设施。
- 做技术选择时如果排除了其他合理方案，追加一条 decision，写清失效条件。不要事后补记。
- 如果实际工作已经偏离 `docs/plan.md`，指出偏离，不要默默继续，也不要自行修改 `docs/plan.md`。
- 连续三个节点都无法关联到任何假设时，主动提出这一点。
- 外部会话记忆、其他项目名称和未注明来源的背景信息不得作为本项目事实。项目事实必须能追溯到仓库文件、数据自带 metadata 或用户在本项目中的明确确认；发现污染时先报告来源与影响，再清除或隔离。
- 暂未解决但尚未造成硬阻塞的问题写入 `docs/ISSUES.md`；一旦满足条目中的升级条件，应明确报告硬阻塞及其对 roadmap 和结论的影响，不能继续标记为普通 issue。
- 当前结构与样本依据只能来自数据自带 metadata。metadata 未提供的信息保持未知，不得从文件名、表达模式或外部常识静默补成确认性标签。
- 默认只使用本地已有数据。需要补充外部数据时，先说明现有证据缺口、拟补数据的不可替代性、规模和预期解锁的判据，经用户批准后再获取。
- CPU 和内存可在不影响系统正常工作的前提下使用；任何任务必须至少保留 1.2 TB 存储余量。
- GPU 当前禁止使用。识别到 GPU 需求时记录用途、CPU 替代方案和时间影响；GPU 禁用使运行时间显著延长并影响进度时，按硬阻塞处理，集中提交用户审核。

### STATUS.md 的写法

每天结束时重写整份文件，覆盖旧内容（历史由版本控制保留）。目标读者是一个完全不了解本项目的人，他读完两分钟内应该知道我们在做什么、进展到哪、下一步是什么。

四段，每段几句话，用日常语言：

1. **我们在回答什么问题** —— 不用术语，一两句。
2. **目前知道了什么** —— 已经得到的结论，以及可信程度。诚实说明哪些还不确定。
3. **今天做了什么** —— 具体做了什么，结果是什么。包括失败和没跑通的部分。
4. **接下来做什么** —— 下一步一到两件事，以及为什么是这件。

不要写成任务清单，不要罗列文件名和函数名，不要用"优化了""完善了"这类无信息的动词。如果今天的工作纯粹是工程性的、无法用科学语言描述，就直接这么写。
